## What was removed, and why

Up to T-2026.10.11 a release had two more files, `colab_notebook.html` and
`colab_notebook_shared.html`: **seven files**.

- They were two saved copies of the signed-out Google Colab web page (title "Google Colab",
  about 93 KB each, alike except for per-request values). They held nothing of this project
  and no notebook content. The four browser API keys in them were that page's own.
- **No code ever loaded them.** Every dialog is built with `HtmlService.createHtmlOutput()`
  from a string in the code; no file is loaded by name anywhere, in any commit.
- They were in the first commit of this repository, were named in the root `.claspignore` when
  that was written, and were copied from there into the list of the release tool. Since then
  every release carried them.

They are removed from the current sources, from the root `.claspignore` and from the release
list. The history is not rewritten: every earlier commit and every release tag still has them.

## Every release keeps its own file set

A release is immutable, and so is the list of its files. T-2026.10.11 and the earlier releases
stay seven files; they are not incomplete five-file releases and they are not invalid.

The adoption mode of the release tool (`--adopt`, also used to roll a report back) therefore
does not measure a release with today's list. It reads the list **from the release's own
tag**: the `RELEASE_FILES` list in `tools/template-release.js` as the tag holds it. Every
release tag holds the tool that built it, so every release says which files it has.

| | From |
|---|---|
| Which files the release has | `RELEASE_FILES` at the tag, plus `Release.js` |
| The content of each source file | the same file at the tag |
| `Release.js` | the built bundle (it records the build time, so it is not in Git) |

- The tool's source at the tag is parsed, not run. If the list cannot be read with certainty,
  nothing is planned; today's list is never used in its place.
- A bundle with a file more or a file less than its tag declares is refused, in both
  generations. A five-file bundle is not accepted for a seven-file tag, nor the reverse.
- Adopting T-2026.10.11 or an earlier release puts the two pages back into that project. That
  is that release, exactly as it was deployed.

As before, adoption copies a built release bundle (`dist/template-release/<release>/`) and
never rebuilds one. It does not use the adoption folders of earlier deployments.

**For the maintainer of the tool:** keep `RELEASE_FILES` as one `['source', 'name']` pair per
line. `tests/release-file-set.test.js` checks that the tool can read its own list.

## At the first five-file deployment

`clasp push` (3.3.0) sends the whole file list, and the script project then holds exactly
those files: the two pages disappear from the project with the first push of a five-file
release. Such a push always differs from the project in `Release.js`, so it is sent. The
read-back after it is **exactly five files** — as always, a deployment is verified by reading
the project back and counting its files, not by the message of the push
(`docs/STATUS_DROPDOWN_MIGRATION.md`, "One thing learned about the tooling").

The records of earlier deployments say "seven files". They are correct and stay as they are.
